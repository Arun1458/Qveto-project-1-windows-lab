## 6. Isolation Design

Both virtual machines are configured to use the same VirtualBox Internal Network. Bridged networking is not part of the intended design.

The lab should not be considered fully isolated until all enabled adapters, routing configuration, and relevant host/guest networking settings have been reviewed.

## 7. Validation

- Windows-to-Kali ping: Successful, 0% packet loss.
- Kali-to-Windows ping: Successful, 0% packet loss after enabling the relevant Windows inbound ICMPv4 Echo Request rule.
- E09–E10 show Adapter 1 on LabNet and Adapters 2–4 disabled on both VMs.
- E11 shows no Windows IPv4 default route, but lists three DNS values in `fec0::/10`; determine whether they are configured or fallback values (E17). E12 shows Kali's connected route and no default route; Kali resolver output remains unverified (E18).
- E13 confirms the named snapshots exist; the Kali snapshot details display Adapter 1 as NAT, so verify the selected snapshot states before using them for lab recovery (E19).
- E12/E16 show Kali's address after restart. E14 records guest OS versions. E15 shows Defender and firewall status, but not real-time protection. Windows Update was previously recorded as up to date in branch history; reconfirm both current statuses (E20–E21).
- The exact host OS version is not recorded (E22).

## 8. Recovery

The recorded baseline snapshots are:

- windows11-clean-install
- kali-clean-install

Snapshot existence is confirmed in E13. Before relying on the Kali snapshot for isolated recovery, reconcile its displayed NAT adapter setting with the current LabNet configuration.

## 9. Conclusion

The documented lab architecture consists of two virtual machines communicating over the Internal Network LabNet. The recorded addresses and successful ping tests demonstrate bidirectional ICMP connectivity. They do not establish complete isolation; see `../evidence/README.md` and `baseline-checklist.txt` for the remaining verification work.

End of lab design.
